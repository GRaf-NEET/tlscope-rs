# TLScope

## 1. Назначение

`TLScope` - локальный отладочный HTTP/HTTPS-прокси для анализа трафика приложений, которые пользователь явно запускает через этот инструмент или явно настраивает на этот explicit proxy.

Основной сценарий:

```bash
TLScope run -- ./target/debug/my_application --config test.toml
```

Инструмент поднимает прокси на `127.0.0.1`, запускает дочерний процесс без shell-склейки аргументов, передаёт ему `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` и варианты в нижнем регистре, показывает запросы в TUI и останавливает прокси после завершения работы.

Программа не перехватывает трафик всей системы и не умеет анализировать произвольный процесс, если он не использует настроенный explicit proxy.

## 2. Правовые и этические ограничения

Используйте программу только для собственных приложений или систем, на тестирование которых у вас есть разрешение.

`TLScope` не реализует и не должен реализовывать:

- скрытый перехват трафика;
- внедрение в чужие процессы;
- ARP/DNS spoofing, packet injection или перенаправление чужого трафика;
- автоматическое изменение системных proxy-настроек;
- автоматическую установку локального CA в системное хранилище;
- обход certificate pinning;
- отключение механизмов безопасности приложения;
- телеметрию или отправку собранных данных во внешнюю сеть.

HTTPS inspection раскрывает содержимое зашифрованных запросов дочернего приложения. Включайте его только в контролируемом тестовом окружении.

## 3. Архитектура

Проект разделён на модули:

```text
src/
  main.rs              CLI entrypoint
  lib.rs               публичные модули для тестов
  cli.rs               clap-команды и параметры
  config.rs            конфигурация запуска
  app.rs               orchestration команд run/proxy/ca

  process/             запуск дочерних процессов
  proxy/               explicit HTTP/HTTPS proxy, CONNECT, TLS, upstream
  certificates/        локальный debugging CA и leaf cache
  capture/             модель сессии, фильтры, redaction, export
  tui/                 ratatui/crossterm интерфейс

tests/                 localhost-only интеграционные тесты
```

Прокси использует HTTP/1.1 для обычных explicit proxy запросов. HTTPS идёт через `CONNECT`: без inspection это TCP-туннель, с inspection прокси завершает TLS от клиента локальным leaf-сертификатом. Если клиент выбирает ALPN `h2`, TLScope обрабатывает HTTP/2 stream-ы и проксирует их к upstream через HTTP/2 по TLS; иначе используется HTTP/1.1 pipeline.

## 4. Сборка

```bash
cargo build
cargo test
cargo clippy --all-targets
```

Используется Rust stable. Если `clippy` не установлен:

```bash
rustup component add clippy
```

## 5. Первый запуск

Самый простой вариант для обычного `.exe`:

```bash
cargo build
./target/debug/TLScope
```

На Windows после сборки можно открыть `target\debug\TLScope.exe`. Без аргументов TLScope сразу откроет стартовое TUI-меню:

- поле `Program or folder` принимает путь к `.exe` или папке;
- если указана папка, появится TUI-список найденных `.exe`;
- в меню можно указать аргументы запуска, рабочий каталог, proxy, CA dir, save-session и настройки секретов;
- после выбора `Start` программа запускается через локальный proxy.

Управление стартовым меню:

```text
Up/Down или j/k - выбрать поле
Enter           - редактировать поле, переключить ON/OFF или запустить
Esc             - отменить редактирование или выйти
```

Пример прямого запуска из терминала:

```bash
cargo run -- run -- ./target/debug/my_application --config test.toml
```

По умолчанию прокси слушает `127.0.0.1:8080`. Для другого адреса:

```bash
TLScope run --listen 127.0.0.1:18080 -- ./my_application
```

Слушать внешний интерфейс можно только с явным флагом:

```bash
TLScope proxy --listen 0.0.0.0:8080 --allow-external
```

Используйте это только в доверенной тестовой сети.

## 6. Создание локального CA

```bash
TLScope ca create
TLScope ca path
TLScope ca fingerprint
```

CA создаётся локально при первом использовании HTTPS inspection. Закрытый ключ хранится только в каталоге CA на компьютере пользователя и не пишется в логи.

Можно указать каталог:

```bash
TLScope ca create --ca-dir ./local-ca
```

## 7. Ручная установка CA для тестового окружения

Программа печатает путь к PEM-файлу CA. Установите этот сертификат вручную только в тестовый trust store того клиента, который вы отлаживаете.

Для дочернего процесса `run` по умолчанию также передаются переменные:

```text
SSL_CERT_FILE
REQUESTS_CA_BUNDLE
CURL_CA_BUNDLE
NODE_EXTRA_CA_CERTS
```

Отключить их можно так:

```bash
TLScope run --no-extra-ca-env -- ./my_application
```

Если приложение использует certificate pinning или игнорирует proxy-переменные, инструмент покажет ошибку TLS/proxy, но не будет пытаться обходить защиту.

## 8. Запуск приложения через инспектор

```bash
TLScope run \
  --listen 127.0.0.1:8080 \
  --ca-dir ./local-ca \
  --max-body-size 1048576 \
  --redact \
  --env RUST_LOG=debug \
  --save-session session.json \
  -- ./target/debug/my_application --config test.toml
```

Полезные параметры:

```text
--no-tls-decryption     туннелировать CONNECT без расшифровки
--workdir <path>        рабочий каталог дочернего процесса
--env KEY=VALUE         дополнительная переменная окружения
--redact                маскировать секретные JSON/form поля
--show-secrets          явно показать секретные значения с предупреждением
--max-body-size <bytes> лимит сохраняемого тела в памяти
--save-session <path>   сохранить JSON сессию при выходе
--no-extra-ca-env       не передавать SSL_CERT_FILE и аналоги
```

## 9. Управление TUI

```text
^/v или j/k  - выбор запроса
Enter        - открыть подробности
Esc          - назад
Tab          - следующая вкладка
Shift+Tab    - предыдущая вкладка
/            - ввод фильтра
Space        - пауза или продолжение отображения
c            - очистить текущую сессию
e            - экспорт JSON в TLScope-export.json
r            - повторно применить фильтр
y            - показать выбранный URL в статусной строке
?            - справка
q            - выход
```

Если дочерний процесс ещё работает, `q` показывает выбор: завершить child, оставить child работать или отменить выход.

Нижняя строка TUI показывает актуальные клавиши для текущего экрана. Если нажать клавишу, которая в этом месте не работает, там же появится короткое объяснение.

## 10. Фильтры

Фильтр состоит из условий, разделённых пробелами. Условия объединяются как логическое `AND`.

```text
method:POST
host:api.example.com
path:/v1/users
status:404
status:>=400
type:json
has:request-body
has:response-body
error:true
tls:false
duration:>500ms
```

## 11. Маскирование секретов

По умолчанию в UI/export скрываются значения заголовков:

```text
Authorization
Proxy-Authorization
Cookie
Set-Cookie
X-Api-Key
```

С флагом `--redact` также маскируются распространённые поля JSON/form:

```text
password, passwd, token, access_token, refresh_token, secret,
api_key, client_secret, credit_card, card_number, cvv
```

Полный показ секретов включается только через `--show-secrets` и сопровождается предупреждением.

## 12. Экспорт

Поддержаны функции экспорта в коде:

- JSON сессии;
- HAR-приближение;
- текстовый отчёт;
- cURL-команда для выбранного запроса.

В TUI клавиша `e` пишет JSON-сессию в `TLScope-export.json`. Параметр `--save-session <path>` сохраняет JSON при завершении программы. Секреты в cURL и JSON по умолчанию остаются скрытыми.

## 13. Ограничения

Текущий MVP стабильно покрывает HTTP/1.1 explicit proxy:

- HTTP/2 поддерживается для HTTPS inspection через `CONNECT` + ALPN `h2`; cleartext h2c и HTTP/2 extended CONNECT для WebSocket-over-H2 пока не реализованы;
- HTTP/1.1 WebSocket upgrade поддерживается как туннель после `101 Switching Protocols`; payload-фреймы считаются в размере обмена, но не декодируются;
- chunked request body возвращает понятную `501 Not Implemented` ошибку;
- HTTP/1.1 inspection внутри CONNECT обрабатывает один запрос на соединение; HTTP/2 inspection может записывать несколько stream-ов как отдельные entries;
- timing показывает только общую длительность, недоступные этапы выводятся как `N/A`;
- инструмент не определяет поток или библиотеку внутри дочернего процесса, сделавшую запрос;
- приложение должно использовать proxy-переменные или быть явно настроено на proxy.

Прокси не отключает проверку upstream-сертификатов. Для локальных тестовых TLS-серверов тесты добавляют отдельный test root только в конфигурацию прокси-теста.

## 14. Удаление локального CA

```bash
TLScope ca remove
```

Команда просит подтверждение и удаляет только файлы, созданные `TLScope` в каталоге CA. Системное хранилище сертификатов не изменяется.

## 15. Устранение неполадок

Порт занят:

```text
cannot listen on 127.0.0.1:8080; port may already be occupied
```

Выберите другой `--listen` или остановите процесс, занимающий порт.

Сертификат не считается доверенным:

Установите PEM из `TLScope ca path` в trust store тестового клиента или используйте переменные `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`.

Приложение не использует прокси:

Проверьте, что приложение уважает `HTTP_PROXY`/`HTTPS_PROXY`, или настройте explicit proxy в конфигурации самого приложения.

TLS handshake failed:

Возможные причины: CA не установлен в trust store клиента, certificate pinning, неверное имя хоста, недействительный upstream-сертификат или сетевой сбой. Инструмент не обходит pinning и не отключает проверку upstream.

DNS не работает:

Проверьте имя host в запросе и доступность DNS на машине, где запущен прокси.

Тело слишком большое:

Увеличьте `--max-body-size` или используйте экспорт только для нужной сессии. Прокси передаёт тело дальше, но хранит в памяти только ограниченный preview и помечает `truncated`.
